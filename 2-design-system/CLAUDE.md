# 2. Design System

Среда, посвящённая дизайн-системе. Самая объёмная среда — строго изолирована от остальных трёх.

## Правила

- Здесь хранится весь скрин дизайн-системы из Figma и само подключение по MCP к Figma.
- Здесь же хранится дизайн-система в разрезе Foundations, и описано, какой компонент за что
  отвечает.
- Среда отвечает за всю связь между тем, что есть в Figma, и тем, что зафиксировано здесь.
  Через эту же среду менеджерятся компоненты и экраны — добавление, изменение — всё, что
  связано с Figma, идёт через неё.
- Строгая изоляция: работать здесь должен только `design-system-agent`. Задачи из других сред
  не выполняются внутри `2-design-system` напрямую — их либо делегируют `design-system-agent`,
  либо не трогают эту среду вовсе.
- Любая правка внутри этой директории требует подтверждения пользователя (см. корневой
  `.claude/settings.json`, правило `ask` для `2-design-system/**`).

## Реестр `figma-map.json`

`2-design-system/figma-map.json` — реестр связи между Figma-файлом и зафиксированной здесь
дизайн-системой. Используется при разборе входящих Figma-ссылок (см. скилл
`figma-mcp-connect`), чтобы не придумывать маппинг заново, а свериться с уже известным.

Схема:
- `project` — `{ fileKey, fileUrl, teamId, name }`, один Figma-файл дизайн-системы на реестр.
- `components[]` — по одному объекту на компонент:
  - `name` — имя компонента как в Figma. **Источник правды: компонент ищется по имени.**
  - `figmaNodeId` — node id из Figma, **кэш-подсказка, а не истина** (см. правило ниже).
  - `page`, `frame` — расположение внутри файла.
  - `purpose` — короткое назначение компонента (одна фраза).
  - `description` — расширенное описание/поведение/варианты.
  - `reactStatus` — есть ли код-аналог (`not-implemented` / `in-progress` / `implemented`).
  - `lastSynced` — дата последней проверки на соответствие Figma (ISO 8601) или `null`.

Кто и когда обновляет: только `design-system-agent`, после каждого значимого изменения в
Figma-файле (новый/изменённый/удалённый компонент) либо после ручной parity-проверки
(сверка содержимого Figma с этим реестром). Правки требуют подтверждения пользователя, как и
любая другая запись в `2-design-system/**`.

Текущее состояние: OAuth к Figma MCP ещё не пройден пользователем, `project` не заполнен,
`components` содержит один явный placeholder-объект — удалить его при первой реальной
регистрации компонента.

### Правило: имя главнее node id

Node id в Figma нестабилен — он слетает, когда компонент пересобирают заново. Имя слетает при
переименовании. Ломаются они по-разному, и в этом всё дело:

- протухшее **имя** даёт честную ошибку «такого компонента нет» — видно сразу, лечится
  пересверкой;
- протухший **id** молча приводит не туда — агент соберёт макет из чужого компонента и ничего
  не заподозрит.

**Уточнение: node id и key — разные вещи.** У опубликованного в библиотеке компонента есть ещё
`key`, и он присваивается раз и навсегда — не слетает ни при пересборке, ни при переименовании
(теряется только при переносе в другую библиотеку). Порядок надёжности:

`key` → имя → `node id`

Если компонент опубликован и `key` известен — он и есть самый надёжный якорь, надёжнее имени.
Имя остаётся источником правды там, где `key` недоступен: у неопубликованных и локальных
компонентов. Правило ниже сформулировано про **node id**, с `key` оно не спорит.

Отсюда правило — *из принципа* «ошибка должна ломаться громко, а не тихо»:

1. Компонент ищется **по имени** (либо по `key`, если он есть). `figmaNodeId` — ускоряющий кэш,
   не источник правды.
2. Карта «имя → текущий node id» строится **в начале сессии** одним проходом по нужной странице
   и живёт в памяти сессии.
3. При расхождении карты и реестра верим имени, `figmaNodeId` в реестре обновляем и проставляем
   свежий `lastSynced`.
4. Если по имени компонент не нашёлся — не подставлять похожий и не идти по старому id.
   Показать пользователю расхождение списком: что появилось, что пропало, что переименовано.

## Токены — `tokens.md`

`2-design-system/tokens.md` — карта переменных и текстовых стилей файла в формате
«имя → значение → для чего». Владелец тот же — `design-system-agent`.

- Источник правды — переменные Figma. Если в проекте появится код с токенами, имена
  сопоставляются, расхождения помечаются явно, но побеждает Figma.
- Перегенерируется при изменении переменных, не правится вручную по памяти.

## Паспорт компонента

Источник идеи — статья Додо о дизайн-системе (Хабр, Сергей Орлов, 2026-08-27); не канон курса.

Новый компонент не собирается, пока не согласован его паспорт. Зачем: спор «мне так кажется»
превращается в аргумент по документу — например, две «разные» кнопки на паспортах оказываются
одним компонентом с разными состояниями.

**Где живёт.** Отдельная страница `Passports` в Figma-файле ДС, две секции: `Design` (короткая
версия) и `Dev` (полная, по одной на каждую платформу, если их несколько). Паспорт компонента —
горизонтальный ряд фреймов слева направо.

**Из чего состоит** (по картинкам статьи; пример там — текстовое поле):
1. **Обложка** — название компонента и предпросмотр.
2. **Изменения в новой версии** — история версий паспорта: что и когда поменялось.
3. **Анатомия** — из каких частей собран (контейнер, заголовок, подпись, курсор, кнопка
   очистки, счётчик), каждая часть подписана на схеме.
4. **Состояния** — как меняется при взаимодействии: default, focused, filled, error, disabled.
5. **Типы** — разновидности компонента (однострочный, многострочный).
6. **Правила поведения** — граничные случаи: переполнение текста, лимит символов, перенос строк.
7. **Анимация** — что и как анимируется при смене состояний: трансформация, параметры, кривая.
8. **Доступность** — требования a11y, в т.ч. RTL.

Дизайнерская версия короче: обложка, изменения, состояния, типы, доступность. Анатомия, правила
поведения и анимация — только в dev-версии, там они нужны для сборки.

- Согласование — через `decision-board` на уровне компонента: паспорт показывается владелице,
  отметки ✔/✘/? (у ✘ причина обязательна), сборка после отметок.
- Ссылка на паспорт кладётся в поле `description` записи компонента в `figma-map.json`.
- Не хватает состояния у существующего компонента — это заявка на доработку компонента (новая
  версия паспорта), а не повод собрать рядом свой вариант.

### Путь компонента

Адаптация схемы Додо под воркспейс (там роли команд, здесь агенты и владелица):

1. Экрану нужен компонент ДС → проверить паспорт: он есть, нужные состояния описаны? Нет — не
   додумывать, вернуться к владелице, `design-system-agent` готовит паспорт.
2. Компонент есть и состояний хватает → `prototyping-agent` берёт и использует, дальше по схеме
   не идёт.
3. Компонента нет → сначала паспорт и отметки на листе (`decision-board`), затем сборка в Figma
   (`design-system-agent`), затем код (`prototyping-agent`) по паспорту и правилам контракта.
4. Обязательные шаги для любого нового компонента: история в Storybook (не опция) и две
   проверки — `design-review` и отметка владелицы. Только после них компонент считается частью
   системы.

## Лист компонента

Формат страницы компонента в `kit-index.html` и в Storybook (по картинкам статьи Додо):

- Тёмный лист на компонент: название сверху, ниже группы вариантов.
- **Заголовок группы называет правило словами**, не только тему: «Прозрачные — сливаются с
  подложкой по замыслу», «Статичные — только поверх цветного слоя».
- Под каждым вариантом подпись — его точное имя в коде или значение параметра, для размеров
  ещё и реальная высота (`large · 52`, `regular · 44`).
- Обязательные группы: размеры, основные стили, состояния (обычное, disabled, progress, для
  вторичного стиля свой disabled), контент (только текст, иконка слева/справа, подзаголовок,
  перенос до N строк).
- Если у компонента есть пары взаимоисключающих флагов (порядок строк цены), каждое значение
  показывается отдельным вариантом с подписью `параметр = значение`.

## Покрытие кодом

Сколько компонентов ДС уже реализовано в коде — считается из поля `reactStatus` в
`figma-map.json`: карточка «N из M компонентов» с процентом и полосой, по платформе, если их
несколько. Для тренда рядом лежит датированный лог снимков (дата, N, M); тренд строится, когда
снимков минимум два. Выводится на страницу `kit-index.html`. Обновляется вместе с реестром.

## Контракт системы — `CONTRACT.md`

`2-design-system/CONTRACT.md` — жёсткие правила, которым обязан подчиняться **любой** экран
системы, вне зависимости от узла или потока. Не растёт органически, как плейбук: это не журнал
грабель, а фиксированный минимум, который проверяется на каждом собранном экране (в т.ч. в
`design-review`).

Обязательный минимум контракта:
- **Каркас экрана** — из чего состоит типовой экран системы (шапка, контент, навигация,
  отступы) и какого размера фрейм.
- **Три закона размеров** — каждый инстанс отвечает на ширину и высоту (авто-лейаут или
  констрейнты); фиксированные размеры только у иконок и аватаров; текст тянется, а не режется.
- **Значения только из токенов** — цвета через переменные, текст через стили. Пиксели на глаз
  запрещены: нет нужного токена — спросить пользователя, а не изобрести.

Правило, поднятое из плейбука в контракт (см. ниже) при третьем повторении одной и той же
ошибки — раз что-то ломается систематически, а не разово, это уже не грабли, а недостающее
правило контракта.

## Плейбук — `playbook.md`

`2-design-system/playbook.md` — накопленные грабли по этой конкретной системе: заглушки,
битые инстансы, особые компоненты, разовые несостыковки. Растёт от сессии к сессии — всё, обо
что споткнулись, дописывается сюда, а не пересказывается заново каждый раз. В отличие от
контракта — это не список требований к каждому экрану, а память о конкретных случаях.

## Кит системы — `kit-index.html`

`2-design-system/kit-index.html` — собранный визуальный обзор системы одной HTML-страницей:
компоненты, поверхности, состояния, чтобы систему можно было пролистать глазами, не открывая
Figma. Не подменяет Figma как источник правды (правило 2 в `design-system-agent.md`) — это
витрина поверх неё, перегенерируется при значимых изменениях состава компонентов, как и
`figma-map.json`.

Не путать с код-версией: рабочий кодовый компонент-браузер (Storybook и подобное) — это
`4-prototyping/app`, зона `prototyping-agent`, не этой среды.
