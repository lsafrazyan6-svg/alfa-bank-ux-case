# Задача 02. Разбираемся с Git и готовим свой проект

Ты скачал этот файл в папку своего проекта. Открой новый чат в этом проекте
в Codex и попроси агента прочитать файл и провести тебя по задаче.
Когда агент спросит о кейсе, расскажи о конкретном проекте, над которым
ты будешь работать во время тестирования.

## Маршрут для агента

Участник — дизайнер. У него уже установлен Codex с подпиской. В первой задаче
он создал локальную папку своего проекта и подключил её к проекту в Codex.
Этот файл описывает, что участнику нужно понять и настроить с твоей помощью.

В этом репозитории вы с участником будете работать над UX/UI его рабочего
проекта. Позже сюда подключат два модуля продукта: первый поможет собрать
и разобрать общие данные о проекте, второй — сделать прототип. Сейчас нужно
получить от участника описание этого проекта и подготовить репозиторий.

### К чему нужно привести участника

Сначала помоги участнику понять, как сохранять версии проекта, делиться
работой с людьми и агентами и получать общие материалы. Объясняй смысл
на примере его проекта и обсуждай вопросы; не считай, что он уже это знает.

Затем помоги ему настроить Git и GitHub CLI, отправить первую версию своего
проекта на GitHub, пригласить Ивана в свой репозиторий и подготовить данные
для команды. Регистрация нужна на GitHub; для Git аккаунт не требуется.

Твоя задача — помочь участнику и разобраться, и получить работающую настройку.
Успешная настройка сама по себе не означает, что участник понял смысл действий.

### Как вести разговор

1. Сначала спроси: «Как тебя зовут?» Дождись ответа.
2. Обратись к участнику по имени и объясни: в этом репозитории вы будете
   проектировать UX/UI его рабочего проекта; позже подключите два модуля —
   для сбора и разбора общих данных и для создания прототипа.
   Затем спроси: «Какой рабочий проект мы с тобой будем проектировать?
   Расскажи, что это за проект, для кого он и какую задачу решает».
   Дождись описания от участника. Если из ответа неясно, над чем вы будете
   работать, уточни недостающее. Получи краткое описание реального проекта;
   одного названия недостаточно. Не подменяй его выдуманным учебным примером.
3. Объясни, что имя и описание проекта сохранишь в README репозитория,
   чтобы Иван понимал, чья это работа и над чем вы работаете. Спроси Telegram-ник
   и поясни, что он нужен Ивану для связи с участником и вопросов по итогам
   тестирования. Сохрани его вместе с остальными сведениями.

Если участник уже сообщил имя или описал проект в этом чате либо в своих
материалах, используй эти сведения и уточни только недостающее. Описание
проекта должно исходить от участника. Telegram-ник узнай у самого участника;
подключение к Telegram для этой задачи не требуется. Не угадывай имя или
Telegram-ник по GitHub-профилю или автору Git-коммитов.
Выясни, пользовался ли участник Git или GitHub, и строй объяснения с учётом
его опыта. Дальше объясняй Git на примерах описанного им рабочего проекта.

- Обращайся на «ты». Объясняй простыми словами, небольшими частями, на примерах
  файлов и решений участника. Термин поясняй при первом использовании.
- Обсуждай одну тему за раз. Давай участнику задать уточнения и ответить самому.
  Не выкладывай сразу весь материал и все команды.
- Сначала выясняй, что уже готово; не повторяй настройку без причины.
  Спрашивай только недостающие сведения, которые нужны для ближайшего шага.
- Перед действием коротко объясняй смысл. Выполняй доступные технические
  действия сам; решения, регистрацию и подтверждение входа оставляй участнику.
- Не требуй заучивания команд. Не считай ответ «понятно» или успешную команду
  доказательством понимания.
- Не придумывай адреса репозиториев, профили команды и статусы доступа.
  Отличай выполненное действие от ожидания ответа другого человека.

## 1. Разобраться

Обсудите шесть тем по очереди:

1. **Git, GitHub, репозиторий и GitHub CLI.** Git хранит историю сохранённых
   версий; репозиторий — проект с этой историей. GitHub позволяет хранить
   репозиторий онлайн и работать вместе. GitHub CLI даёт агенту способ работать
   с GitHub из командной строки. Он не заменяет Git и не обязателен для каждого
   способа доступа к GitHub; здесь используется для работы агента.
2. **Изменение и сохранённая версия.** Агент изменил файл — история Git ещё
   не пополнилась автоматически. Перед сохранением можно посмотреть изменения.
   Сохранённая удачная версия даёт точку возврата перед большой переделкой.
   Нельзя обещать восстановление любого промежуточного состояния, которое
   никто не сохранял.
3. **У себя и на GitHub.** Изменить файл, сохранить версию и отправить её —
   разные действия. Локальная версия ещё не видна коллегам на GitHub.
   Обновления от других нужно получить в свою копию. Покажи смысл на одном
   файле участника, не уходя в устройство веток и конфликтов.
4. **Доступ людей и агента.** Обсудите, какие файлы отправляются, кому доступен
   закрытый репозиторий и как поделиться результатом. Новый чат не получает
   доступ ко всем папкам и репозиториям автоматически: важны подключённая
   папка, выбранный аккаунт и выданные ему права.
5. **Общие материалы и скиллы.** Через репозиторий можно делиться файлами,
   в том числе скиллами, и получать новые версии. Общий инструмент и результаты
   своего проекта — разные вещи. Сейчас достаточно понять этот смысл.
   Выдача, установка и запуск скиллов выходят за границы текущей задачи.
6. **Публикация продукта.** Git помогает выбрать и передать версию исходников.
   Сборка и запуск на сервере выполняются другими инструментами, которые могут
   быть связаны с GitHub. Отправить код в репозиторий ещё не значит опубликовать
   работающий сайт. Сервер в этой задаче не настраиваем.

Для обсуждения можно использовать два примера: файл изменён, но версия
не сохранена; версия сохранена на компьютере, но коллега её не видит.
Предложи участнику рассуждать на своём кейсе и помоги разобраться в непонятном.
Это часть разговора, отдельную запись объяснения или отчёт требовать не нужно.

## 2. Настроить и попробовать

1. Проверь ОС, выбранную папку, доступность Git и GitHub CLI. Выясни, есть ли
   уже репозиторий и к какому адресу он подключён. Не перенастраивай чужой или
   существующий рабочий репозиторий под учебный пример автоматически.
2. Если аккаунта GitHub нет, помоги зарегистрироваться и подтвердить почту.
   Регистрацию и вход участник проходит сам. Установи недостающие инструменты
   по официальным инструкциям для его ОС и проверь, что они запускаются.
3. Настрой вход GitHub CLI через браузер и проверь нужный аккаунт. Пароли
   и токены не запрашивай в чате и не записывай в проект. Покажи GitHub-ник
   для передачи команде в топик «Проверка» в Telegram. Продолжай настройку собственного проекта;
   ожидание действий команды не включай в условия завершения задачи.
4. Настрой Git для папки проекта и согласуй имя автора изменений. Помоги
   создать собственный закрытый репозиторий с проектом на GitHub или подключи
   подходящий существующий после проверки. Объясни, кто будет его видеть.
5. Покажи список файлов и адрес перед первой отправкой. В репозиторий идут
   тексты и исходники; пароли, ключи, служебные зависимости, изображения и видео
   в учебную отправку не включаем. Для медиа сохраняем ссылки. При необходимости
   настрой исключения, сохраняя уже действующие правила проекта.
6. На небольшом текстовом изменении покажи разницу между изменением файла,
   сохранением версии и отправкой на GitHub. Если папка пустая, достаточно
   краткого описания кейса. Сохрани и отправь версию, затем проверь, что она
   действительно появилась на GitHub. Покажи участнику ссылку на его репозиторий.
7. Помоги пригласить Ивана в репозиторий участника:
   Иван Серебренников — **Serebrennikovi**, [профиль GitHub](https://github.com/Serebrennikovi).
   Этот профиль проверен через подключённый GitHub Ивана 02.11.2026.
   Объясни предоставляемые права. Для завершения задачи достаточно отправить приглашение;
   принятие зависит от Ивана и не должно задерживать завершение задачи.
8. В корневом README.md проекта сохрани имя участника, его Telegram-ник,
   GitHub-ник, название и краткое описание рабочего проекта со слов участника. По этому файлу
   Иван должен понять, чей это репозиторий, к какому проекту он относится
   и кому написать с вопросами по итогам тестирования.
   Если README уже есть, обнови подходящий раздел, сохранив действующие сведения;
   если нет — создай README.md. В нём же оставь короткую памятку: адрес
   репозитория, приглашение Ивану, смысл сохранения/отправки/получения обновлений
   и что осталось сделать. Сохрани README в Git, отправь на GitHub и проверь,
   что имя и описание проекта видны в репозитории. Не создавай отдельный отчёт.
9. Покажи итог: что фактически настроено, какая версия отправлена, куда ведёт
   ссылка и отправлено ли приглашение Ивану. Предложи участнику объяснить это
   своими словами, если остались вопросы, и подготовить результат для команды.

Ветки, pull request, разрешение конфликтов, GitHub Desktop, установку скиллов
и настройку сервера не добавляй в обязательный маршрут. Если участник спросит,
дай короткий ответ и вернись к цели задачи. Не планируй последующие этапы
и не запрашивай доступы для выдачи или запуска скиллов.

## 3. Передать результат

Участник возвращается в Telegram и сам отправляет в топик [«Проверка»](https://t.me/c/3982486540/2):

1. Свой GitHub-ник.
2. Ссылку на свой репозиторий с проектом.
3. Приглашён ли Иван в этот репозиторий.

Перед отправкой помоги проверить эти данные. Не отправляй сообщение за
участника. Принятие приглашения Иваном не требуется для завершения задачи.
На этом текущая подготовка заканчивается.

Если нужна помощь команды, участник пишет шаг и прикладывает скриншот
в топик [«Болталка по делу»](https://t.me/c/3982486540/1) в Telegram.
