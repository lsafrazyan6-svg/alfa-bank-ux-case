# 4. Prototyping

Среда, посвящённая прототипированию.

## Цель

Итог работы в этой среде — один из трёх результатов (по запросу владельца):
1. **Реальное работающее приложение** — задеплоенное, не просто макет.
2. **Хорошо работающий прототип на локальном хосте по ссылке** — адаптивный (отрабатывает разные
   размеры экрана), не хрупкий демо-скрин.
3. **Код по ссылке на макет в Figma** — дать ссылку на фрейм, получить закодженный результат и
   ссылку на рабочую версию.

Держать в уме этот конечный ориентир при любой задаче в среде, не останавливаться на статичной
вёрстке без адаптива, если владелец не просил только это.

Если результат №1 — это нативное iOS-приложение (не веб на React), путь к нему отдельный, через
скилл `iphone-app`: экраны сначала проходят `decision-board` (лист решений с отметками
владельца), потом сборка в `4-prototyping/app/` под Xcode/симулятор, а не через
`figma-to-proto`.

## Правила

- Должна иметь зеркальное отображение того, что есть в `2-design-system`.
- Так же, как и `2-design-system`, собирает экраны, подключаясь по MCP к Figma (доступ read-only:
  только выгрузка экранов/фреймов, см. `.agents/skills/figma-mcp-connect/SKILL.md`).
- Изоляция не строгая: среда может при необходимости взаимодействовать с другими средами, но по
  умолчанию задачи должны выполняться в рамках своей собственной среды, а не расползаться по
  чужим.
- Читает `2-design-system` только для чтения — зеркалирует её, но никогда не пишет туда.

## Синхронизация с Figma и Design System

Прототипы не должны дублировать содержимое дизайн-системы. Вместо копирования описаний
компонентов — ссылка на источник правды.

**Источники правды (только чтение, не копировать):**

- `2-design-system/figma-map.json` — реестр компонентов ДС и их Figma ID
  (схема: `project` + `components[{ name, figmaNodeId, page, frame, purpose, description }]`).
  Ведётся `design-system-agent`.

**Реестр этой среды:**

- `4-prototyping/screens-map.json` — реестр экранов прототипа. Формат и назначение полей описаны
  в комментарии внутри самого файла (`_meta`).

### Правило связывания

Каждый экран/прототип, который использует компонент из дизайн-системы, обязан ссылаться на него
по `component.name` из `2-design-system/figma-map.json`, а не пересказывать его
свойства/описание внутри `4-prototyping/`. Имя — источник правды, `figmaNodeId` — только
кэш-подсказка (правило «имя главнее node id» в `2-design-system/AGENTS.md`). Если нужного
компонента ещё нет в `figma-map.json` — сообщить пользователю, не придумывать локальное
описание вместо него.

## Порядок сборки экрана

Работать по реестру, а не сканировать Figma-файл заново на каждый запрос — иначе уходит контекст
и агент промахивается мимо компонентов.

1. **Выбор компонентов — по `2-design-system/figma-map.json`.** В Figma ходить точечно, только
   за теми узлами, которые реально используются на экране.
2. **Карта узлов — один раз в начале сессии.** Собрать соответствие «имя компонента → текущий
   node id» для нужной страницы и работать по ней; в файлы её не сохранять.
3. **План до сборки.** Показать пользователю текстом состав экрана: какие компоненты, в каком
   порядке, что в данных. Собирать после подтверждения, а не сразу.
4. **Собирать в отдельном Figma-файле с подключённой библиотекой**, а не внутри файла самой
   дизайн-системы: дубликаты коллекций переменных ломают привязку. Это же следует из запрета
   писать в `2-design-system/`.
5. **Самопроверка после сборки** — по плейбуку ДС (`2-design-system/playbook.md`): значения из
   токенов, каждый инстанс отвечает на ширину и высоту, текст не обрезан. Новые грабли
   дописываются в плейбук, а он в чужой среде — значит через `design-system-agent`, не самим.

## Вайрфреймы — доска структуры до стиля

Первый визуальный шаг проекта, до дизайн-системы и `decision-board`: доска серых каркасов всех
экранов одной HTML-страницей, `4-prototyping/wireframes/` (скилл `wireframe-board`). Владелица
ставит ✔/✘/? на доске; экран без ✔ дальше не идёт. Собирает `prototyping-agent`.

## Холст потока — навигируемая карта собранных экранов

Когда поток экранов согласован через `decision-board` (холст-версия листа решений — см. скилл,
раздел «Холст») и собран — тот же холст не выбрасывается, а встраивается в прототип как
отдельная навигируемая страница: все экраны потока со стрелками переходов из
`4-prototyping/screens-map.json` (пунктир — обратимые), пан/зум, клик по подписи приближает
экран. Для кодового прототипа — рядом с код-браузером компонентов (Storybook или аналог, если
он есть в проекте), а не вместо него: Storybook показывает компоненты по отдельности, холст —
как они складываются в поток целиком.

## Git и GitHub (для кодовых проектов)

Применимо только к продуктовым проектам, которые ведутся как настоящий код (не только сборка
экранов по ДС в Figma). Корень воркспейса не git-репозиторий и им не становится — репозиторий
заводится точечно, внутри `4-prototyping/app/` конкретного проекта, и только по явной просьбе
владелицы, не проактивно. Один код-проект — один репозиторий, без вложенных репозиториев поверх
других сред того же проекта (`1-research/`, `2-design-system/`, `3-content/` в git не входят).
Работа через `gh` (создание репозитория/PR) и коммиты — по общему протоколу git-безопасности из
корневого `AGENTS.md`: без `--force`/`--no-verify` без явной просьбы, `git status` перед
разрушительными операциями, коммит только по запросу.

### Расхождения

Если обнаружено расхождение между прототипом и `2-design-system/` или актуальным состоянием в
Figma (устаревший `figmaFrameId`, изменившийся компонент, отсутствующая запись в
`figma-map.json` и т.п.) — **не исправлять самостоятельно** ни в `2-design-system/`, ни задним
числом в Figma. Сообщить пользователю и, при необходимости правки самой ДС, явно
переадресовать задачу `design-system-agent`. В `screens-map.json` такой экран следует пометить
`status: "stale"`.
